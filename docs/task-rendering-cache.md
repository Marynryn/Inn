Глобальное `'/**': { 'Cache-Control': 'no-store' }` снять. Правила сливаются, а не замещают друг друга — на кешируемых маршрутах заголовок задать явно.

- Глобального no-store нет, каждый маршрут имеет осознанное правило.

- TTFB на повторном запросе главы заметно ниже первого.
- Значений, зависящих от даты, в кешируемых ответах нет.

## Задача B. Публичный эндпоинт зависит от роли — ✅ СДЕЛАНО 4 ноября

### Проблема

Список глав фильтруется по роли внутри общего эндпоинта. Под админом в ответ попадают неопубликованные главы, и они уезжают в payload страницы.

Пока кеша нет — данные видит только админ. С включённым swr достаточно после деплоя зайти на сайт под собой, и неопубликованные главы попадут в кеш, который получат все читатели.

nuxt-auth-utils от этого не защищает: он убирает из payload только свою сессию. Собственный useFetch по-прежнему форвардит cookie, и API по-прежнему видит админа.

То же самое у персонажей. `/api/characters/index.get.ts` фильтрует по isAdmin (спрятанные карточки) и отдаёт `lit` из `flames.mine` — то есть сразу две болезни: роль и персональное поле.

В цифрах (1 ноября): payload главной под админом на ~4,4 тыс. символов больше, чем у читателя (44 903 против 40 493) — сессия (~500) и данные, которые видит только админ, в первую очередь черновики.

### Что сделать

Развести пути. Публичный эндпоинт всегда отдаёт только опубликованные главы, независимо от того, кто спрашивает. Админка ходит в отдельный `/api/admin/chapters`.

Группа `/api/admin/chapters/*` уже существует — post, [id].put, [id].delete, reorder.put. GET-списка среди них нет, admin.vue по-прежнему ходит в публичный `/api/chapters`. То есть правка укладывается в один новый файл плюс одна строка в admin.vue.

Заодно убрать `isPublished` из публичного ответа вовсе: в публичном списке по определению только опубликованные, а отсутствие поля делает утечку физически невозможной, а не «отфильтрованной».

### Критерии приёмки

- Ответ публичного эндпоинта не содержит `isPublished: false` ни при каких условиях.
- `/api/characters` не зависит ни от роли, ни от сессии.
- Тест, который дёргает публичный эндпоинт с админской сессией и падает, если в ответе есть неопубликованное. Playwright в проекте уже стоит.

### Сделано 4 ноября

**Главы.**

- `server/api/chapters/index.get.ts` сессию не читает вовсе: всегда только опубликованные, поля `isPublished` в ответе нет.
- Новый `server/api/admin/chapters.get.ts` — все главы с `isPublished`. Права проверяет `server/middleware/admin-guard.ts`, как у остальной группы `/api/admin`.
- `app/pages/admin.vue` ходит в `/api/admin/chapters`.

**Персонажи.**

- `/api/characters` не зависит ни от роли, ни от сессии, ни от IP: спрятанных карточек в нём нет ни для кого, полей `lit` и `hidden` нет.
- Новый `/api/characters/lit` — id персонажей, которым этот человек зажёг огонёк (по аккаунту, гость — по IP, как раньше).
- Новый `/api/admin/characters` — полный список со спрятанными и пометкой `hidden`.
- `server/utils/character-flames.ts`: `flameSummary` разделён на `flameCounts()` (общее) и `myFlames(event)` (личное).
- `app/pages/characters.vue`: на сервере рендерится общий список; в браузере после монтирования подсвечиваются свои огоньки, а админу список заменяется полным из `/api/admin/characters` (по `watch` на `auth.isAdmin`, потому что пользователь в сторе появляется не сразу).
- `app/pages/game.vue` грузит карточки так же: общий список плюс свои огоньки.
- Тип `PublicCharacter` и `toCharacter()` — в `shared/utils/characters.ts`.

**Тесты** (`tests/e2e`):

- `admin.spec.ts` › «публичный список глав не зависит от того, кто спрашивает»: черновик, запрос под админской сессией — черновика нет, `isPublished` нет, ответ побайтово равен гостевому; в `/api/admin/chapters` черновик есть. Плюс `/api/admin/chapters` гостю — 403.
- `characters.spec.ts` › «общий список карточек одинаков для всех, свои огоньки — отдельно»: читатель зажигает огонёк, его `/api/characters` побайтово равен гостевому, `/api/characters/lit` у читателя содержит персонажа, у гостя — нет, на странице огонёк подсвечивается.
- Тест про спрятанную карточку дополнен: админский `/api/characters` её тоже не содержит, а после перезагрузки страницы админ видит её с пометкой.

**Что осталось за рамками B.**

- `/api/chapters/[id]` (одна глава) по-прежнему отдаёт админу черновик — так админ читает его до публикации. Для кеша это значит: при включении swr на `/chapter/[id]` (задача A) админский заход на черновик положит его в кеш по адресу черновика. Решать в A: либо админ смотрит черновик по отдельному адресу или с `?preview`, либо черновики вне кеша.
- Огоньки гостей по-прежнему по IP — тот же вопрос «cookie вместо IP», что в задаче C.
- Подсветка своих огоньков появляется после гидратации. Вёрстку это не двигает (меняется только класс), так что к задаче D не относится.

## Задача C. Комментарии персонализированы через myReaction — ✅ СДЕЛАНО 5 ноября

### Проблема

В `/api/comments` поле `myReaction` вычисляется по сессии, а для анонимов — по IP-адресу. Список грузится через useFetch, то есть попадает в payload.

При swr первый, кто прогреет кеш, раздаст всем свои подсветки: остальные увидят лайки уже нажатыми. Не дыра в безопасности, но выглядит как поломка и воспроизводится случайно.

Второй эффект, не связанный с кешем: за одним NAT (мобильный оператор, офис) читатели видят реакции друг друга уже сейчас.

### Что сделать

Не отдавать `myReaction` вместе со списком — запрашивать состояние реакций отдельным запросом с клиента после гидратации, с `server: false` и обязательным `default`. Сами комментарии остаются в серверном HTML и индексируются.

Отдельно решить, чем опознавать анонима. Cookie вместо IP — та же правка, и она же снимает вопрос, нужны ли здесь ворота `enabled` (на 4.5.2 опция уже доступна).

### Критерии приёмки

- В серверном HTML кешируемой страницы нет ни одного поля, зависящего от сессии или IP.
- Подсветка своих реакций работает после гидратации.
- Два читателя за одним NAT не видят реакции друг друга.

### Сделано 5 ноября

- `GET /api/comments` больше не читает ни сессию, ни IP: в ответе только общие счётчики `likes` и `dislikes`, поля `myReaction` нет. Из рассылки нового комментария по вебсокету оно тоже убрано.
- Новый `GET /api/comments/reactions?chapterId=…` (или `?siteWide=1`) — `{ [id комментария]: "like" | "dislike" }`, только свои: вошедший — по аккаунту, гость — по куке.
- `CommentSection.vue` берёт свои реакции через `useFetch` с `server: false`, `lazy: true` и `default: () => ({})`, перезапрашивает их после реакции и при входе или выходе. Сами комментарии по-прежнему в серверном HTML.
- **Гость опознаётся по куке, а не по IP.** `server/utils/anon-id.ts`: кука `tavern_anon` (случайный UUID, httpOnly, SameSite=Lax, 2 года). Заводится только когда гость ставит реакцию; просто чтение её не создаёт. В `comment_reactions` добавлен столбец `anon_id` (миграция в `server/utils/migrate.ts`, плюс частичный индекс).
- Ворота `enabled` не понадобились: запрос своих реакций и так идёт только из браузера.

**Тесты** (`tests/e2e/comments.spec.ts`):

- «два гостя за одним IP не видят реакций друг друга» — общий `x-forwarded-for`, первый лайкает, после перезагрузки его лайк подсвечен, у второго — нет, и его `/api/comments/reactions` пуст.
- «серверный HTML обсуждения не зависит от того, кто его смотрит» — читатель с лайком и гость получают побайтово одинаковый `/api/comments`, в серверном HTML страницы нет подсвеченной кнопки.

**Чем заплатили.**

- Старые гостевые реакции (с одним `ip`, без `anon_id`) остаются в счётчиках, но больше ничьи: гость, лайкнувший до перехода на куки, не увидит свою подсветку и сможет лайкнуть ещё раз. Один раз на комментарий.
- Куку стереть проще, чем сменить IP: гость, который хочет накрутить лайки, теперь может это делать чаще. Для лайков под комментариями это приемлемо; если накрутка появится — ограничивать по IP число реакций гостя в сутки, а не опознавать по нему.
- Подсветка своих реакций появляется после гидратации. Вёрстка не двигается — меняется только класс кнопки.
- Огоньки персонажей у гостей по-прежнему по IP (`server/utils/character-flames.ts`). Тот же переход на `anonId()` — отдельная небольшая правка, с заменой уникального индекса `character_flames_ip`.

## Задача E. Плашка «прочитано» пропадает после F5 — ✅ СДЕЛАНО 11 октября

Решение — ровно то, что планировалось: решение стало вычисляемым вместо снимка в onMounted.

```ts
const alreadyMarked = computed(() => isRead(chapterId))
const justMarked = ref(false)
const showReadMarker = computed(() => alreadyMarked.value || justMarked.value)
```

Плюс `{ passive: true }` на слушателе скролла и onUnmounted на верхнем уровне рядом с onMounted — две правки из задачи H заодно.

Правило, которое из этого выведено (оно уже в конспекте M1, §3.11): если данные могут приехать позже, не записывай решение в ref внутри onMounted — делай computed. Одноразовый снимок состояния при монтировании ломается ровно на разнице «клиентский переход / перезагрузка», и поэтому проявляется как баг, который воспроизводится только по F5.

## Задача F. Почистить payload — ✅ СДЕЛАНО 11 октября

300 → 116 КБ распакованных. Четыре приёма, и два из них оказались лучше того, что планировалось.

**1. Текст главы не едет в данные страницы вообще.** Вместо pick поверх полного ответа — отдельный режим эндпоинта:

```ts
const { data: chapter, error } = await useFetch(`/api/chapters/${encodeURIComponent(rawParam)}`, {
  query: { meta: 1 },
  pick: ['id', 'volume', 'title', 'publishedAt', 'isPublished', 'commentsCount', 'description'],
})
```

Текст рисует серверный компонент ChapterText. Это строго лучше, чем просто pick: pick режет только payload, а сервер всё равно отдаёт текст по сети при клиентской навигации. `?meta=1` убирает его из ответа, а остров — из клиентского бандла. Побочный плюс: query входит в вычисление автоключа, то есть метаданные и полный ответ не делят ячейку.

**2. Страница обсуждения просит у эндпоинта только заголовок:**

```ts
const { data: chapter, error } = await useFetch(`/api/chapters/${encodeURIComponent(rawId)}`, {
  query: { meta: 1 },
  key: `chapter-head:${rawId}`,
  pick: ['id', 'title'],
})
```

**3. transform для навигации** — из списка остаются только id и sortOrder.

**4. pick для настроек** — вместо всей таблицы (включая текст «О проекте») только то, что рисуют шапка и плашка телеграма.

### Инструмент: разбор payload в консоли на проде

Открыть страницу, F12 → Console, вставить целиком, Enter (если Chrome просит — сначала напечатать `allow pasting`). Показывает общий размер `__NUXT_DATA__` и таблицу всех записей payload, самые тяжёлые сверху.

```js
(() => {
  const el = document.getElementById('__NUXT_DATA__')
  const raw = JSON.parse(el.textContent)
  const special = { '-1': undefined, '-2': undefined, '-3': NaN, '-4': Infinity, '-5': -Infinity, '-6': -0 }
  const seen = new Map()

  // расшифровка devalue: числа в объектах — номера ячеек массива
  const hydrate = (i) => {
    if (i < 0) return special[i]
    if (seen.has(i)) return seen.get(i)
    const v = raw[i]
    if (v === null || typeof v !== 'object') { seen.set(i, v); return v }
    if (Array.isArray(v)) {
      if (typeof v[0] === 'string') {           // ["ShallowReactive",1], ["Date","..."] и т.п.
        const [type, ...rest] = v
        let out
        if (type === 'Date') out = v[1]
        else if (type === 'Set') out = rest.map(hydrate)
        else if (type === 'Map' || type === 'null') {
          out = {}
          for (let k = 0; k < rest.length; k += 2) {
            out[type === 'Map' ? String(hydrate(rest[k])) : rest[k]] = hydrate(rest[k + 1])
          }
        } else out = typeof v[1] === 'number' ? hydrate(v[1]) : v[1]
        seen.set(i, out); return out
      }
      const arr = []; seen.set(i, arr)
      for (const n of v) arr.push(hydrate(n))
      return arr
    }
    const obj = {}; seen.set(i, obj)
    for (const k in v) obj[k] = hydrate(v[k])
    return obj
  }

  const payload = hydrate(0)
  const rows = []
  const add = (key, val) => {
    const s = JSON.stringify(val) ?? ''
    rows.push({ key, chars: s.length, preview: s.slice(0, 100) })
  }
  for (const [top, val] of Object.entries(payload)) {
    if (['data', 'state', 'pinia'].includes(top) && val && typeof val === 'object') {
      for (const [k, v] of Object.entries(val)) add(`${top}.${k}`, v)
    } else add(top, val)
  }

  console.log('Весь __NUXT_DATA__:', el.textContent.length, 'символов')
  console.table(rows.sort((a, b) => b.chars - a.chars))

  // разбивка одной записи по полям
  window.__payload = payload
  window.__fields = (key) => {
    let v = payload.data?.[key]
    if (!Array.isArray(v)) v = Object.values(v ?? {}).find(Array.isArray) ?? [v]
    const sizes = {}
    for (const item of v) {
      for (const [f, x] of Object.entries(item ?? {})) {
        sizes[f] = (sizes[f] ?? 0) + f.length + (JSON.stringify(x) ?? '').length
      }
    }
    console.log('Записей:', v.length)
    console.table(Object.entries(sizes).sort((a, b) => b[1] - a[1]).map(([field, chars]) => ({ field, chars })))
  }
})()
```

Разбивка записи по полям — по куску ключа из таблицы, чтобы не потерять `$` в начале:

```js
__fields(Object.keys(__payload.data).find(k => k.includes('2vpuda')))
```
